# 无人机视觉拦截项目工程评估报告

**项目概述**: 使用上视相机和比例导引法（PNG）实现无人机自主拦截
**评估日期**: 2026-07-09
**当前状态**: 已完成 PX4/AirSim 仿真验证，准备转向 Betaflight 实机部署

---

## 执行摘要

本项目实现了基于纯视觉的比例导引拦截系统，核心技术路线为：固定上视相机 → YOLO目标检测 → 视线角（LOS）/碰撞时间（TTC）估计 → 比例导引控制。项目已在 AirSim/PX4 环境中完成仿真验证，当前正准备迁移至 Betaflight 实机平台。

本评估报告从工程实践角度分析了当前方案的优势、风险点和可优化方向，重点关注从仿真到实机的迁移挑战，以及 Betaflight 平台的工程适配问题。

**主要结论**:
- ✅ 架构设计合理，模块化良好，具备工程可维护性
- ⚠️ 单目视觉 TTC 估计在实际环境中可靠性存在挑战
- ⚠️ Betaflight MSP 控制路径与 PX4 差异较大，需要独立调试
- ⚠️ 视觉处理延迟和帧率对末端拦截性能影响显著
- ✅ 安全机制设计完备，具备多层次保护

## 1. 当前方案技术架构分析

### 1.1 系统架构优势

**模块化设计**
项目采用了清晰的分层架构，将视觉感知、状态估计、导引算法和飞控适配分离：
- 视觉前端（YOLO + ByteTrack）独立于导引算法
- 6D LOS 滤波器和 TTC 估计器相互独立
- 飞控适配层（PX4/Betaflight）通过统一接口接入

这种设计的优势：
- 各模块可独立测试和验证
- 便于在不同硬件平台间迁移
- 易于后续算法优化和替换

**渐进式验证路径**
从合成数据 → AirSim 仿真 → Betaflight 实机的三阶段验证策略符合工程实践：
- 单元测试覆盖核心算法
- 仿真环境验证完整链路
- 实机前有充分的台架测试流程

**完善的日志和诊断系统**
Betaflight 实现中包含详尽的日志记录：
- 记录了从原始检测到最终控制输出的全链路数据
- 包含安全状态机的所有门控条件
- 支持离线回放和分析

这对实机调试至关重要，可以快速定位问题根源。

### 1.2 核心技术路线评估

**纯视觉比例导引方法**
当前采用的纯视觉 PNG 方案：
```
视线角速率 λ̇ (从 bbox 中心) + TTC 增益调度 K(TTC) → 导引指令
```

**优势**：
- 不依赖测距传感器，硬件成本低
- 比例导引是经典的拦截制导方法，理论基础扎实
- 视线角测量相对可靠（bbox 中心定位精度较高）

**局限**：
- TTC 估计依赖 bbox 面积变化，对目标姿态变化、相机曝光变化敏感
- 无法获得真实距离和闭合速度，末端控制精度受限
- 对视觉丢帧和检测抖动敏感

**6D LOS Kalman 滤波器设计**
使用 6 维状态 `[λx, λy, λz, λ̇x, λ̇y, λ̇z]` 跟踪视线角及其变化率：

**优势**：
- 强制视线向量归一化，符合角度测量的物理约束
- 视线角速率投影到垂直于视线的平面，避免非物理估计
- 通过姿态历史查表实现相机-惯性坐标系转换，考虑了机体运动

**可优化点**：
- 滤波器参数（过程噪声、观测噪声）需要根据实际视觉性能调优
- 当前未考虑目标机动模型，纯恒速假设可能不足
- 创新度（innovation）门控阈值需要实测数据标定

**TTC（Time-to-Contact）估计**
基于 bbox 面积变化率估计碰撞时间：`TTC ≈ A / Ȧ`

**已知的工程挑战**：
1. **面积变化的多因素耦合**：
   - 距离变化（真正需要的信号）
   - 目标姿态变化（干扰）
   - 相机曝光/对焦变化（干扰）
   - YOLO 检测框抖动（噪声）

2. **边界裁切问题**：
   - 目标靠近画面边缘时 bbox 被裁切
   - 裁切会导致面积突变，污染 TTC 估计
   - 当前方案已考虑裁切检测，但这会限制有效制导区域

3. **数值稳定性**：
   - 面积导数接近零时 TTC 会发散
   - 面积导数为负（目标远离）时 TTC 无意义
   - 需要鲁棒的饱和和限幅策略

**建议**：
- 考虑引入多尺度 TTC 估计（不仅用总面积，也用 bbox 宽度、高度的几何平均）
- 研究基于光流的 TTC 估计作为备选方案
- 在有条件时引入低成本测距传感器（毫米波雷达、ToF）作为 TTC 的验证通道

## 2. 从 PX4 到 Betaflight 的迁移挑战

### 2.1 架构差异分析

**控制接口的本质差异**

PX4 架构（当前仿真使用）：
- Offboard 模式支持多种高层指令：速度、姿态、体轴角速率、推力
- MAVLINK 协议通信，消息丰富且标准化
- 飞控内部有完整的外环控制器（位置→速度→姿态→角速率）

Betaflight 架构（目标实机平台）：
- 主要面向 FPV 竞速，设计理念是"人遥控"
- MSP 协议主要用于配置和遥测，控制通道有限
- `MSP_SET_RAW_RC` 本质是模拟遥控器输入，不是机载计算机控制接口
- 无外环控制器，只有内环姿态/角速率稳定

**当前项目的适配策略**

项目采用的方案是：
```
导引评估量 g_eval → rate_gain_matrix → roll/pitch/yaw rate → RC 通道映射
```

这是一个**务实的工程选择**，因为：
- Betaflight 没有标准的 Offboard 接口
- 避免修改 Betaflight 固件，降低维护成本
- 利用 Betaflight 成熟的内环控制器

但也带来了挑战：
- 需要重新标定 `rate_gain_matrix`（PX4 的 body-rate 参数不能复用）
- RC 通道映射需要精确配置（通道顺序、方向、限幅）
- 丢失了 PX4Offboard 模式的一些高级功能（如速度保持）

### 2.2 关键工程风险点

**1. 时间同步和延迟**

PX4/AirSim 仿真环境：
- 时间可以是仿真时间，确保严格同步
- 视觉和姿态数据的时间戳来自同一时钟

Betaflight 实机环境：
- 相机时间戳和 MSP 姿态时间戳可能来自不同时钟源
- 机载计算机（如 Jetson）和飞控时间需要同步或标定偏差
- 视觉处理、MSP 通信、控制计算都有延迟，累计延迟可能达到 50-200ms

**影响**：
- 姿态查表失败或插值误差增大
- 视线角估计存在系统性偏差
- 末端机动时延迟导致脱靶

**建议措施**：
- 实测端到端延迟（从目标运动到飞控响应）
- 考虑在视线角速率中引入运动补偿
- 如果延迟过大（>150ms），需要增加预测环节

**2. 视觉帧率限制**

AirSim 仿真中视觉帧率可以较高（30-60 FPS），但实机环境受限于：
- 机载计算平台性能（如 Jetson Nano vs. Orin）
- YOLO 模型复杂度（YOLOv8n vs. YOLOv8l）
- 图像分辨率和后处理开销

**实际帧率可能只有 10-20 FPS**

**影响**：
- LOS 角速率估计的时间分辨率降低
- TTC 面积导数估计噪声增大
- 末端快速接近阶段更新率不足

**建议**：
- 优化 YOLO 推理（TensorRT 加速、INT8 量化）
- 降低输入分辨率（640x640 → 416x416）但需评估检测距离损失
- 考虑使用更轻量的检测器（如 YOLO-FastestV2）用于近距离末端
- 在低帧率下增强滤波器的预测能力

**3. RC 通道映射的复杂性**

Betaflight 的 RC 通道配置非常灵活，但也容易出错：
- 通道顺序（AETR、TAER 等）需要与飞控配置一致
- 通道方向（正负）需要逐个确认
- 中位值、最大最小值可能因接收机而异
- AUX 通道分配受限（通常最多 8 通道）

项目中已经实现了 `RcCommandMapper`，支持：
- 可配置的通道映射
- rate 到 RC us 的转换
- 限幅和斜率限制
- 详细的诊断日志（raw、clipped、slew_limited）

这是**很好的工程实践**，但仍需注意：
- 台架测试时必须无桨验证方向和幅度
- 使用 Betaflight Configurator 的 Receiver 选项卡实时查看
- 记录实际飞行时的 `rc_clipped` 和 `rc_slew_limited` 标志，用于调参

**4. 安全逻辑的完备性**

项目实现的 `BetaflightSafetyStateMachine` 已经考虑了多层保护：
- 控制权限（`--control-mode` 和 `--allow-control`）
- AUX 开关使能
- 遥测和姿态数据新鲜度
- 电池电压监控
- 导引目标有效性
- Watchdog 超时保护

**优势**：
- 多层门控确保任一条件失效时退出自主控制
- 非 active 状态发送中性 RC，避免保持上一帧指令
- 状态和原因都记录在日志中，便于事后分析

**可增强的方向**：
- 考虑增加过载保护（如果能获取加速度计数据）
- 增加地理围栏（如果有 GPS 数据）
- 增加"退出高度"逻辑（高度过低时强制退出自主模式）
- 考虑与人工遥控器的优先级和接管逻辑（当前依赖 Betaflight 的 Failsafe）

## 3. 视觉感知系统的工程挑战

### 3.1 YOLO 检测的实际性能

**仿真 vs 实际的差距**

AirSim 仿真环境：
- 目标外观稳定，光照可控
- 无运动模糊，无大气衰减
- 背景相对简单

实际飞行环境：
- 目标可能有遮挡、姿态变化、光照变化
- 高速运动时可能有运动模糊（尤其是 rolling shutter 相机）
- 天空背景相对简单，但可能有云、建筑物、其他飞行器

**建议的工程实践**：
1. **数据集准备**：
   - 采集实际飞行环境的目标图像
   - 包含不同距离、角度、光照条件
   - 标注并微调 YOLO 模型

2. **检测性能指标**：
   - 不仅看 mAP，更要关注：
     - 最大检测距离（vs. 所需拦截距离）
     - bbox 中心定位精度（vs. LOS 估计需求）
     - 漏检率（尤其是连续漏检）
     - 误检率（天空背景下的飞鸟、气球等）

3. **在线性能监控**：
   - 记录检测置信度（score）分布
   - 记录 track id 切换频率
   - 记录 bbox 抖动幅度

### 3.2 目标跟踪策略

**当前方案：ByteTrack**

ByteTrack 是一个轻量且有效的多目标跟踪器，适合实时场景。

**优势**：
- 不需要目标外观特征提取（ReID），计算开销小
- 利用低置信度检测恢复短期遮挡
- 对检测器输出的依赖相对简单

**在拦截场景中的特点**：
- 拦截通常是单目标场景，ByteTrack 的多目标能力未充分利用
- 拦截末端目标会充满画面，可能导致 bbox 裁切后跟踪失败
- track id 切换会导致 LOS 滤波器和 TTC 估计器重新初始化，引入瞬态

**可选的优化方向**：
1. **单目标模式优化**：
   - 如果确定是单目标拦截，可以简化为"最近检测 + 卡尔曼预测"
   - 减少 track id 切换，仅在长时间丢失后才重新初始化
   - 利用导引指令预测目标在画面中的运动

2. **末端视场保持策略**：
   - 当 bbox 接近画面边缘时，降低横向导引增益，优先保持目标在视场内
   - 项目中提到的 "frame centering" 辅助项可以在这方面发挥作用
   - 考虑在末端切换为"保持视线对准"而非"最大接近率"

3. **丢失后的盲推（Blind Push）**：
   - 当前方案提到了 "terminal extrapolation"
   - 如果 LOS 角速率稳定，丢失后短时间内可以外推视线方向
   - 但需要严格限制盲推时间（如 0.5-1 秒），避免大幅偏离

### 3.3 相机配置和标定

**固定上视相机的约束**

优势：
- 无需云台，减少机械复杂度和重量
- 无云台伺服延迟和控制耦合
- 相机外参固定，标定一次即可

挑战：
- 视场保持完全依赖机体姿态控制
- 大幅机动时目标易出视场
- 上视布局对地面测试不友好（需要悬挂目标）

**关键标定参数**：

1. **相机内参**：
   - 焦距 `fx, fy`
   - 主点 `cx, cy`
   - 畸变系数（如果使用广角镜头）

   内参误差直接导致视线角系统性偏差。建议：
   - 使用棋盘格标定
   - 实际飞行环境温度下标定（温度会影响镜头）
   - 验证标定精度（重投影误差 < 0.5 像素）

2. **相机外参 `R_BC`**：
   - 相机相对于机体坐标系的旋转
   - 项目中使用 `pitch_up_deg` 简化配置（假设只有俯仰偏移）

   外参误差会导致视线角在机体系的转换错误。建议：
   - 使用目标测试验证（悬停对准已知方向的目标，检查 LOS 估计）
   - 考虑相机安装的机械公差（±2-3°）
   - 如果有条件，通过实际飞行数据做闭环标定

3. **时间戳和延迟**：
   - 相机曝光时间戳的获取方式
   - 图像传输延迟
   - YOLO 推理延迟
   - MSP 通信延迟

   建议：
   - 端到端延迟测试（LED 闪烁 + 日志时间戳分析）
   - 如果延迟 > 100ms，考虑在控制律中补偿

## 4. 控制系统设计的工程考量

### 4.1 比例导引参数调优

**增益调度 K(TTC) 的设计**

当前方案使用 TTC 作为增益调度信号：
```
g_eval = K(TTC) × λ̇
```

**设计意图**：
- TTC 大（距离远）时，小增益，避免过早消耗能量
- TTC 小（接近目标）时，大增益，提高末端机动能力

**实际工程中的挑战**：
1. **TTC 估计的可靠性问题**：
   - 如前所述，bbox 面积 TTC 存在多种干扰
   - 如果 TTC 估计跳变，增益调度会导致控制指令突变

2. **增益调度的平滑性**：
   - 需要使用平滑函数（如 sigmoid、tanh）
   - 避免分段线性导致的导数不连续

3. **参数标定的困难**：
   - K(TTC) 的形状参数（斜率、转折点）需要大量飞行测试
   - 不同目标速度和机动模式下最优参数可能不同

**建议的工程实践**：
- **保守起步**：初期测试使用固定小增益，不启用增益调度
- **数据驱动调参**：收集不同场景的飞行数据，离线优化 K(TTC) 参数
- **备选方案**：考虑基于距离估计（如果引入测距传感器）或基于 bbox 面积阈值的分段增益
- **饱和保护**：确保 K(TTC) 有上下限，避免极端值

### 4.2 从导引指令到飞控输入的映射

**PX4 路径（仿真中使用）**：
项目在 AirSim/PX4 中实现了多种映射：
- Velocity setpoint
- Body-rate + thrust
- Attitude + thrust

这些是高层指令，PX4 内部有控制器闭环。

**Betaflight 路径（实机目标）**：
```
g_eval → rate_gain_matrix → roll/pitch/yaw rate → RC 通道
```

这是一个**开环映射**，缺少外环控制。

**关键差异的影响**：

1. **无速度保持**：
   - PX4 的 velocity 模式会自动抵消风扰、保持期望速度
   - Betaflight 的 rate 模式只稳定角速率，水平速度会漂移
   - 在拦截场景中，如果需要悬停或慢速接近，Betaflight 路径会困难

2. **无高度保持**：
   - 项目中设置 `thrust = hover_thrust` 尝试保持高度
   - 但这是开环的，无法补偿负载变化（电池消耗）、风扰
   - 长时间飞行会缓慢下降或上升

3. **rate_gain_matrix 的标定挑战**：
   - 这个矩阵将 `g_eval` (惯性系导引量) 映射到 roll/pitch/yaw rate
   - 需要考虑：
     - 坐标系转换（惯性系 → 机体系）
     - 机体动力学特性（质量、转动惯量、推重比）
     - Betaflight 内环控制器的响应特性
   - 目前配置中默认为零矩阵，需要实机标定

**标定 rate_gain_matrix 的建议流程**：

1. **台架测试**：
   - 无桨状态，给定小幅 `g_eval` 输入
   - 观察 Receiver 选项卡中的 RC 通道输出
   - 确认符号和方向正确

2. **悬停响应测试**：
   - 系留或低速悬停
   - 给定阶跃或正弦 `g_eval` 输入
   - 记录姿态响应和实际运动
   - 调整矩阵增益使响应适度（不过冲、不迟钝）

3. **闭环拦截测试**：
   - 从远距离、低速目标开始
   - 逐步增加目标速度和机动幅度
   - 监控控制饱和（`rc_clipped`）和机体姿态限制

4. **迭代优化**：
   - 分析脱靶距离（CEP）与 `rate_gain_matrix` 的关系
   - 注意过大增益可能导致震荡，过小增益导致响应不足

### 4.3 RC 通道斜率限制

项目中实现的 `max_delta_us_per_s` 是一个**重要的工程安全特性**。

**作用**：
- 限制 RC 通道的变化率
- 避免视觉抖动、检测突变、TTC 跳变直接形成阶跃控制指令
- 提供平滑的控制输出，降低机械应力和电机负载

**参数选择的考量**：
- 太小：控制响应迟钝，无法快速机动
- 太大：失去保护作用
- 典型值：相当于 0.5-1 秒内从中位到最大行程

**建议**：
- 初期测试使用较小的斜率限制（保守）
- 监控日志中的 `rc_slew_limited` 标志
- 如果频繁触发斜率限制，说明：
  - 视觉输入噪声过大，需要优化检测或滤波
  - 或者导引算法产生过激指令，需要调整增益
- 如果从未触发斜率限制，可以适当放宽（提高响应性）

### 4.4 失效模式和降级策略

**当前方案的失效处理**：

项目中的安全状态机定义了多种状态：
- `LOG_ONLY`：默认只记录，不输出控制
- `DISABLED`：控制权限未启用
- `READY`：条件满足但 AUX 未使能
- `ACTIVE`：正常自主控制
- `DEGRADED`：部分条件失效（如目标丢失）
- `FAILSAFE`：严重失效（如遥测超时）

非 `ACTIVE` 状态时输出中性 RC 或不输出，避免保持上一帧指令。

**优势**：
- 明确的状态定义，便于理解和调试
- 多层门控确保安全
- 详细的 `safety_reason` 记录便于事后分析

**可增强的方向**：

1. **目标丢失后的短期保持**：
   - 当前方案在目标丢失时立即退出 `ACTIVE`
   - 可以考虑短时间（0.5-1s）内维持最后的导引方向（外推）
   - 但需要严格限制外推时间和最大姿态角，避免失控

2. **分级降级策略**：
   - 轻微失效（如 TTC 无效但 LOS 有效）：降低增益继续导引
   - 中度失效（如目标丢失但 watchdog 未超时）：保持姿态或缓慢回中
   - 严重失效（如遥测超时）：立即中性 RC，依赖 Betaflight Failsafe

3. **与人工遥控的协作**：
   - 当前主要依赖 AUX 开关和 Betaflight 的 Failsafe 机制
   - 可以考虑"混合模式"：自主系统提供辅助，人工遥控保持优先级
   - 需要明确接管逻辑和指示（如 LED、蜂鸣器）

## 5. 实际部署的工程建议

### 5.1 硬件选型

**机载计算平台**

性能需求：
- YOLO 推理（YOLOv8n @ 640×480）：需要 20-50 ms/帧
- ByteTrack + LOS/TTC 计算：5-10 ms
- MSP 通信和控制计算：< 5 ms
- 目标：总延迟 < 100 ms，帧率 > 15 FPS

**推荐选项**：
1. **Jetson Nano**（4GB）：
   - 优势：成本低（~$99），功耗适中（5-10W）
   - 劣势：算力有限，可能需要优化模型或降低分辨率
   - 适合：初期验证、小型无人机

2. **Jetson Orin Nano**（8GB）：
   - 优势：算力显著提升，支持更大模型和更高分辨率
   - 劣势：成本和功耗较高
   - 适合：高性能需求、大载重无人机

3. **其他选项**：
   - Raspberry Pi 5 + Coral TPU：低成本，但 YOLO 部署复杂度高
   - Intel NUC + 独立显卡：高性能，但重量和功耗大

**相机选型**

关键指标：
- 帧率：≥ 30 FPS（实际处理可能低于此）
- 分辨率：640×480 至 1280×720（更高分辨率增加计算负担）
- 视场角（FOV）：60-90° 水平 FOV 平衡检测距离和视场范围
- 接口：MIPI-CSI（低延迟）优于 USB（可能有帧缓冲延迟）
- 快门类型：全局快门（Global Shutter）优于卷帘快门（Rolling Shutter），避免运动模糊

**推荐选项**：
- Raspberry Pi Camera Module 3（或其宽视场版本）
- FLIR Blackfly S（工业级，全局快门，但成本高）
- 自定义 MIPI-CSI 相机模组（淘宝上有多种选择，注意选全局快门型号）

**飞控和机架**

Betaflight 兼容飞控：
- 选择有足够 UART 接口的飞控（至少 2 个：1 个用于机载计算机 MSP，1 个用于遥控接收机）
- 推荐 F7 或 H7 系列（性能和接口更丰富）
- 确保支持 MSP Override 或类似功能

机架选型：
- 足够的载重能力（机载计算机 + 相机 + 电池）
- 上视相机的安装位置和避震
- 电源分配（确保计算平台电源稳定）

### 5.2 分阶段测试策略

项目文档中已有详细的测试流程，以下补充工程实践要点：

**阶段 1：台架集成测试（无桨）**

目标：验证硬件连接、软件部署、基础功能

检查项：
- [ ] MSP 通信正常（`telemetry_error` 为空）
- [ ] 相机图像采集正常，时间戳合理
- [ ] YOLO 检测能识别测试目标
- [ ] 姿态历史缓存工作正常（`attitude_age_s` 合理）
- [ ] 手动旋转机体，观察 LOS 估计变化
- [ ] RC 通道映射正确（Receiver 选项卡验证）
- [ ] AUX 开关能正确触发状态转换
- [ ] 日志记录完整，meta JSON 保存正确

关键工具：
- Betaflight Configurator（查看 Receiver、Modes、Motors）
- 实时查看日志 CSV（可以用 Python 脚本实时绘图）
- 悬挂测试目标或使用屏幕显示目标图片

**阶段 2：系留/围栏测试**

目标：验证基础飞行控制，标定初始参数

检查项：
- [ ] 机体能稳定悬停（人工遥控）
- [ ] 启用自主模式后机体不发散
- [ ] `rate_gain_matrix` 方向正确（给定导引指令，机体朝预期方向机动）
- [ ] 悬停时电池电压和电流合理
- [ ] 热管理正常（计算平台和电机不过热）
- [ ] 通信链路稳定（无频繁的遥测超时）

系留方案：
- 使用长绳限制飞行范围
- 或在室内使用围网
- 确保人工接管方式明确（AUX 开关 + 遥控器优先）

**阶段 3：静止/慢速目标测试**

目标：验证完整拦截链路，低风险场景

测试设置：
- 目标：悬停的另一架无人机，或系留升空的气球
- 距离：10-20 米，逐步减小
- 机动：拦截器从远处接近，不追求碰撞

检查项：
- [ ] LOS 跟踪稳定，`los_innovation_norm` 合理
- [ ] TTC 估计趋势正确（接近时 TTC 减小）
- [ ] 导引指令使机体朝目标运动
- [ ] 接近到一定距离（如 2-3 米）能稳定保持
- [ ] 分析 CEP（圆概率误差）和脱靶量

**阶段 4：移动目标测试**

目标：验证动态拦截性能

目标运动模式：
- 匀速直线（基准场景）
- S 型机动（项目中已有测试）
- 圆周轨迹
- 随机机动

逐步提升难度：
- 目标速度：5 m/s → 10 m/s → 15 m/s
- 拦截角度：迎头 → 侧向 → 追击
- 环境复杂度：无风 → 微风 → 中等风速

关键指标：
- CEP（圆概率误差）
- 最小脱靶距离
- 拦截成功率（定义"成功"为脱靶距离 < 阈值，如 1 米）
- 控制饱和频率
- 丢失目标率

### 5.3 参数标定和调优流程

**相机参数标定**

工具：OpenCV 的标定工具或 MATLAB Camera Calibrator

流程：
1. 打印棋盘格标定板（A3 或更大）
2. 采集 20-30 张不同角度和距离的图像
3. 运行标定算法，获取内参和畸变系数
4. 验证：用标定结果反投影，检查重投影误差

外参标定：
- 机械测量 + 悬停对准已知目标
- 如果可能，通过飞行数据做闭环优化

**YOLO 模型训练/微调**

如果使用通用 COCO 预训练模型，可能需要微调：
1. 采集实际飞行环境的目标图像（不同距离、角度、光照）
2. 标注（可以用 Roboflow、LabelImg 等工具）
3. 在预训练模型基础上微调（transfer learning）
4. 验证：测试集的 mAP、不同距离的检测率

或者使用合成数据增强：
- 将目标 3D 模型渲染到天空背景
- 模拟不同姿态、距离、光照

**LOS 滤波器参数**

需要调整的参数：
- 过程噪声协方差 `Q`
- 观测噪声协方差 `R`
- 创新度门控阈值

调参方法：
- 离线：用记录的飞行数据回放，调整参数直到滤波输出平滑且响应及时
- 在线：逐步调整，观察 `los_innovation_norm` 和导引平滑性

**TTC 估计参数**

需要调整的参数：
- 面积滤波器时间常数
- 面积导数滤波器时间常数
- 裁切检测阈值
- TTC 饱和上下限

调参方法：
- 用实际接近场景的数据分析 TTC 曲线
- 对比不同滤波参数下的 TTC 噪声和延迟
- 选择平滑性和响应性的折中

**控制增益标定**

`rate_gain_matrix` 和增益调度 `K(TTC)`：
- 从保守值开始（小增益）
- 逐步放大，记录脱靶距离
- 找到性能和稳定性的平衡点
- 不同目标速度可能需要不同增益

RC 斜率限制：
- 初期保守（如 500 us/s）
- 如果限制频繁触发且控制响应不足，放宽限制
- 如果从不触发，可以适当收紧（提高对异常的保护）

## 6. 与成熟方案的对比和借鉴

### 6.1 工业无人机拦截系统

**典型方案特点**：
- 多传感器融合：雷达 + 光电（可见光 + 红外）+ 测距
- 专用飞控系统，支持高层导引指令
- 双机或多机协同
- 高可靠性要求，冗余设计

**与本项目的差异**：
- 本项目：纯视觉、单目、低成本
- 目标：技术验证和算法研究，而非产品级可靠性

**可借鉴的经验**：
1. **多模导引阶段**：
   - 远距离：搜索和粗接近（可以用 GPS/IMU 辅助）
   - 中距离：视觉导引
   - 近距离：末端机动和碰撞规避（如果是非破坏性拦截）

2. **失效检测和模式切换**：
   - 明确的模式转换条件和回退机制
   - 本项目的安全状态机已部分体现这一思想

3. **测试和验证方法**：
   - 硬件在环仿真（HIL）
   - 分阶段的包线扩展（本项目已采用）

### 6.2 FPV 竞速无人机自主化项目

一些 FPV 社区的自主飞行项目（如穿越赛道的自主化）提供了 Betaflight 平台的工程经验：

**典型技术路线**：
- Betaflight + MSP 通信
- 机载计算机（Jetson/Pi）+ 相机
- 视觉 SLAM 或标记点识别
- RC 通道注入控制

**常见挑战和解决方案**：
1. **MSP 通信可靠性**：
   - 使用高波特率（115200 或更高）
   - 实现重传和超时检测（本项目已有）
   - 监控错误率，记录日志

2. **RC 覆盖（Override）逻辑**：
   - 明确人工接管优先级
   - 使用 AUX 开关作为使能（本项目已采用）
   - 一些项目使用混合模式（自主 + 人工修正）

3. **延迟优化**：
   - 使用 MIPI-CSI 相机（低于 USB 延迟）
   - 优化 YOLO 推理（TensorRT、量化）
   - 减少中间缓冲和复制

**可借鉴的最佳实践**：
- Betaflight 的 Modes 选项卡配置"auto"模式，关联 AUX 开关
- 日志同步记录（Betaflight Blackbox + 机载计算机日志）
- 台架测试工具（如固定机架 + 风扇模拟动力）

### 6.3 学术研究中的视觉拦截案例

文献中常见的视觉拦截研究：

**常用方法**：
- 视线角导引（LOS guidance）
- 比例导引（PN/APN）
- 模型预测控制（MPC）
- 强化学习（RL）

**本项目采用的比例导引方法**：
- 优势：理论成熟，计算简单，实时性好
- 劣势：对目标机动的适应性有限（无预测）

**学术方案 vs 工程实现的常见差距**：
1. **假设的理想性**：
   - 学术：假设完美状态估计、无延迟、无限机动能力
   - 工程：传感器噪声、延迟、饱和约束

2. **评估指标**：
   - 学术：仿真中的 CEP、拦截成功率
   - 工程：还需考虑可靠性、成本、维护性

3. **鲁棒性**：
   - 学术：特定场景下性能优化
   - 工程：需要在多种干扰下仍能安全运行

**本项目的工程实践亮点**：
- 从仿真到实机的完整链路
- 详细的日志和诊断系统
- 多层次的安全保护
- 模块化设计便于迭代

**可进一步增强的方向**（参考前沿研究）：
1. **目标机动预测**：
   - 当前 LOS 滤波器假设目标恒速
   - 可以引入目标加速度估计或多模型滤波（IMM）

2. **自适应增益**：
   - 根据实时性能（如 LOS 跟踪误差）动态调整导引增益
   - 机器学习方法学习最优增益调度

3. **端到端学习方法**：
   - 用深度学习直接从图像生成控制指令
   - 但需要大量数据和仿真训练，可解释性降低

## 8. 可优化和改进的方向

基于以上分析，以下是按优先级排序的改进建议：

### 8.1 高优先级（建议尽快实施）

**1. 端到端延迟测量和补偿**
- **现状**：文档中提到延迟问题，但未见实测数据
- **改进**：
  - 设计延迟测试方案（如 LED 标记 + 时间戳分析）
  - 量化各环节延迟（相机、YOLO、MSP、控制）
  - 如果总延迟 > 100ms，在控制律中加入延迟补偿
- **预期收益**：降低末端脱靶距离 10-30%

**2. TTC 估计的质量门控增强**
- **现状**：已有基础门控（裁切、面积过小），但可能不足
- **改进**：
  - 增加"目标姿态变化检测"（如 bbox 长宽比突变）
  - 增加"光照变化检测"（如平均亮度突变）
  - 考虑 TTC 估计的方差作为置信度指标
  - 制定 TTC 失效时的降级策略（纯 LOS 导引）
- **预期收益**：降低误导指令，提高鲁棒性

**3. YOLO 推理优化**
- **现状**：可能帧率不足（取决于硬件）
- **改进**：
  - 部署 TensorRT 加速
  - 尝试 INT8 量化（需要标定数据集）
  - 对比不同 YOLO 模型（YOLOv8n/s/m）的性能和精度权衡
  - 考虑动态分辨率（远距离高分辨率、近距离低分辨率）
- **预期收益**：帧率提升 1.5-3 倍

**4. rate_gain_matrix 标定工具和流程**
- **现状**：文档说明需要标定，但无详细工具
- **改进**：
  - 开发台架标定脚本（给定 g_eval，记录 RC 输出）
  - 开发悬停响应分析脚本（给定阶跃输入，分析姿态响应）
  - 文档化标定步骤和常见问题
- **预期收益**：加快调试速度，降低试错成本

### 8.2 中优先级（实机验证后考虑）

**5. 多尺度或多方法 TTC 估计**
- **现状**：仅用 bbox 总面积
- **改进**：
  - 尝试用 bbox 宽度、高度分别估计
  - 考虑光流法 TTC（计算密集，但可能更鲁棒）
  - 多方法融合或投票
- **预期收益**：TTC 估计更鲁棒，但增加计算负担

**6. 目标机动预测**
- **现状**：LOS 滤波器假设恒速
- **改进**：
  - 引入目标加速度状态
  - 或使用交互式多模型（IMM）滤波器
- **预期收益**：对机动目标的拦截性能提升

**7. 自适应增益调度**
- **现状**：增益调度 K(TTC) 使用固定参数
- **改进**：
  - 根据实时 LOS 跟踪误差调整增益
  - 或使用在线学习方法优化
- **预期收益**：不同场景下性能更优

**8. 混合控制模式**
- **现状**：纯自主或纯人工
- **改进**：
  - 实现"辅助模式"：自主系统提供建议，人工遥控器保持控制权
  - 或"分轴模式"：自主控制水平，人工控制高度和航向
- **预期收益**：降低风险，便于渐进式信任建立

### 8.3 低优先级（长期改进方向）

**9. 引入低成本测距传感器**
- **选项**：毫米波雷达（如 TI AWR1243）、ToF 传感器
- **改进**：
  - 提供独立的距离和闭合速度测量
  - 与视觉 TTC 融合或交叉验证
- **挑战**：增加硬件复杂度、重量、成本

**10. 端到端深度学习方法**
- **方法**：用 CNN/Transformer 从图像直接输出控制指令
- **改进**：
  - 可能提升性能，尤其是在复杂场景
  - 需要大量标注数据或仿真训练
- **挑战**：可解释性差，调试困难，泛化性存疑

**11. 多机协同拦截**
- **方法**：多架无人机协同拦截一个或多个目标
- **改进**：
  - 提高拦截成功率
  - 覆盖更大空域
- **挑战**：通信、协调、安全性复杂度大幅增加

3. **安全第一**：保守的初始参数、明确的接管逻辑、充分的风险预案

**策略层面**：

2. **适时引入传感器**：如果视觉方案局限明显，考虑低成本测距传感器
3. **保持灵活性**：模块化设计便于替换算法或传感器
4. **管理预期**：纯视觉单目拦截有其固有局限，设定合理的性能目标

## 11. 最新学术研究对标分析（2024-2025）

本节基于近期检索到的多篇同领域论文，特别是与本项目高度相似的"捷联单目相机 + 多旋翼拦截"方向的研究。这些是**当前最相关的工程参考**，其中部分论文的技术路线与本项目几乎完全对应。

> **重要趋势提示**：2024-2025 年的多旋翼视觉拦截文献**明显从经典比例导引（PN）转向图像视觉伺服（IBVS）**，或采用 PN + IBVS 融合方案。这一趋势值得本项目重点关注。

### 11.1 最相关论文：北航"IBVS + PNG 融合拦截"（IEEE TIE 2025）

**论文**：Precise Interception Flight Targets by Image-Based Visual Servoing of Multicopter（arXiv 2409.17497，IEEE TIE 2025）

这是**与本项目最相似、参考价值最高**的一篇。核心是将 IBVS 与 PNG 融合，仅用单目相机测量的角度信息拦截非合作目标，灵感来自游隼捕食。

**技术路线对比**：

| 环节 | 本项目 | 该论文 |
|------|--------|--------|
| 相机 | 固定上视捷联相机 | 捷联单目相机（120° FOV）|
| 制导 | `g_eval = K(TTC)·λ̇` | PNG：`dσ/dt = K·dq/dt`，3D 分解为两个 2D 平面 |
| 视场保持 | frame centering 辅助项 | 双目标 FOV 控制器（不要求收敛到中心）|
| 延迟处理 | 尚未实测补偿 | 延迟卡尔曼滤波器（DKF）|
| 飞控 | Betaflight（目标）| PX4 |

**可直接借鉴的关键参数**（该论文仿真与实飞一致）：
```
制导常数 K_y = K_z = 3        （对应经典 PN 的 N=3）
加速度控制 k_a = 2
偏航 PD 控制器 k_p = 0.03, k_d = 0.01
```

**核心创新对本项目的启示**：

1. **FOV 保持不要求目标收敛到图像中心**（重要！）：
   - 该论文采用双目标策略：`e_x → 0`（水平方向收敛），`Δe_y ≤ ε`（垂直方向只要求运动范围最小）
   - 这与本项目的"上视相机视场保持"问题直接相关
   - **建议**：本项目的 frame centering 不必强制目标居中，只需保证不出视场，可释放更多机动自由度

2. **通过限制加速度控制 LOS 误差**：
   - 该论文用 `Δq_d ≤ arctan(k_a/g)` 限制动力学引起的视线误差
   - **建议**：本项目可借鉴此思路，将 RC 斜率限制与视线保持关联

**实测性能数据**（极具参考价值）：

| 目标模型 | 纯 PN 误差 | 该论文 IBVS+PN 误差 |
|----------|-----------|---------------------|
| 恒速(CV) | 0.71 m | **0.09 m** |
| 恒加速(CA) | 0.92 m | **0.45 m** |
| 正弦机动(SM) | 0.31 m | **0.04 m** |

静态目标 CEP 达 **0.089 m**（厘米级），相比纯 PN 有数量级提升。

**关键工程经验教训**：
- 硬件：Jetson Xavier NX + Pixhawk 6C Mini + CSI 单目相机（120° FOV）
- 目标气球直径 16cm，无人机轴距 15cm（尺寸接近，拦截极具挑战）
- **风速鲁棒性**：风速 < 4 m/s 时成功率 > 80%，但 6 m/s 时降至 40%
- **重要提醒**：作者明确指出真实非合作目标（无人机、鸟、风筝）"不像气球那样随风摆动"，气球实验有其局限

**对本项目的直接建议**：
- 纯 PN（本项目当前方案）在末端法向加速度激增，导致精度下降；IBVS+PN 融合能显著改善
- 考虑在末端引入 IBVS 分量，直接从图像误差生成控制，而非仅依赖 LOS 角速率

### 11.2 高速拦截的延迟处理（北航 IEEE TCST 2024）

**论文**：High-Speed Interception Multicopter Control by Image-Based Visual Servoing（arXiv 2404.08296）

这篇论文**专门解决延迟问题**，对本项目的延迟风险有直接指导意义。

**关键数据**：
- 终端速度：**20 m/s**（高速）
- 成像 + 图像处理延迟：**约 80-100 ms**
- **在 20 m/s 时，80ms 延迟可导致高达 2 米的控制误差**

这个数据**印证了本报告第 8.1 节的判断**：延迟是影响末端精度的关键因素。

**延迟卡尔曼滤波器（DKF）方法**：
- 延迟期间按无延迟方式更新协方差
- 延迟测量到达时加修正项
- 效果："延迟期间次优估计，延迟后最优估计"
- 18 维状态向量：姿态四元数、相对位置/速度、图像特征点、陀螺仪与加速度计偏置

**双环控制结构**（对本项目的 Betaflight 映射有参考价值）：
```
外环共线控制器（50 Hz）：保证目标在视场内
内环姿态控制器（200 Hz）：速度与姿态精确跟踪
```

**对本项目的直接建议**：
1. **必须实测端到端延迟**：本项目文档反复提到延迟但未实测，这是当前最大空白
2. **考虑延迟补偿**：如果目标速度 > 10 m/s，80ms 延迟就会显著影响精度
3. **控制频率分层**：Betaflight 内环已有 200Hz+ 角速率控制，外环视觉伺服可运行在较低频率（如视觉帧率 15-30Hz）

### 11.3 持久拦截与视觉丢失应对（北航 IEEE TAES 2026）

**论文**：A Unified and Persistent Interception Control of Multicopters With Strapdown Monocular Camera（IEEE TAES 2026）

标题几乎与本项目完全一致——**捷联单目相机多旋翼拦截**，是最直接的对标。

**核心创新**：
- 将球面成像模型融入蒙特卡洛定位（MCL），估计相对方位角
- **关键突破：即使目标飞出视场，仍能精确估计相对方位**
- 统一的 IBVS 控制方案，同时适用于初次拦截和再拦截阶段

**对本项目"目标丢失"问题的直接启示**：
- 本报告第 4.4 节讨论的"目标丢失后短期保持"，该论文提供了系统方法（MCL 方位估计）
- 相比本项目当前的"简单外推"，MCL 能在目标脱离视场后维持定位
- 拦截成功率相比单次拦截方法和 SE(3)-EKF 方法有显著提升

**工程建议**：
- 本项目的上视相机视场有限，目标丢失是高频事件
- 可考虑引入类似 MCL 的方位估计，提高"再拦截"能力
- 但 MCL 计算量较大，需评估 Jetson 平台的实时性

### 11.4 比例导引用于多旋翼的评估（AIAA 2021）

**论文**：Evaluation of Proportional Navigation for Multirotor Pursuit（AIAA 2021）

这是**PN 应用于多旋翼的经典评估论文**，直接验证本项目技术路线的可行性。虽然发表较早，但仍是 PN 用于多旋翼最直接的参考。

**相关论文补充**：
- Toward Increased Airspace Safety: Quadrotor Guidance for Targeting Aerial Objects（arXiv 2107.01733）
- An Intercept and Following Strategy for a Multi-rotor Platform using a Modified Proportional Navigation（AIAA 2019）

这些论文共同表明：**PN 用于多旋翼拦截是可行的，但需要针对多旋翼的动力学特性做修改（Modified PN）**，而非直接套用导弹的 PN。

### 11.5 快速响应 PN 与重复拦截（捷克 CTU，IEEE RA-L）

**论文**：Towards Safe Mid-Air Drone Interception（arXiv 2405.13542）

这篇论文来自捷克技术大学，用**挂网飞行机器人**捕获非合作无人机，提供了大量真实飞行经验。

**关键发现——传统 PN 的一个重要缺陷**：
> 传统 PN 在脱靶后 LOS 角速率接近零，导致响应过慢，这对**需要重复尝试**的无人机拦截不可接受。

**改进方法 FRPN（Fast Response Proportional Navigation）**：
- 在线性化 PN 基础上增加一个与相对位置成正比的项（权重 W）
- 加快初次与重复接战速度，精度损失可忽略

**对本项目的启示**：
- 本项目是"撞击式"拦截，若首次未命中，传统 PN 的重复拦截能力弱
- 可借鉴 FRPN，增加位置相关项提高响应速度

**其他重要工程经验**：
- 用 100 条轨迹、近 14 小时飞行数据做定量对比
- 状态估计用交互多模型（IMM）滤波器，融合 CV 和 CA 模型（**印证本报告 8.2 节"目标机动预测"建议**）
- 选择挂网而非发射网（发射网拦截次数有限）
- 真实实现了对 **5 m/s 飞行目标**的拦截

### 11.6 综合启示：本项目的技术路线定位

基于以上最新研究，对本项目技术路线的评估：

**✅ 本项目方向正确的部分**：
1. 捷联单目相机 + PN 是学术界验证过的可行路线（多篇北航、捷克 CTU 论文）
2. TTC/LOS 分离处理符合主流做法
3. 安全机制和渐进测试符合工程规范

**⚠️ 值得重新考虑的部分**：

1. **纯 PN vs IBVS+PN 融合**：
   - 最新研究（IEEE TIE 2025）显示 IBVS+PN 融合精度比纯 PN 高一个数量级
   - **建议**：本项目可在现有 PN 基础上，末端引入 IBVS 分量
   - 本项目的 `g_eval = K(TTC)·λ̇` 已是 PN 形式，增加图像误差反馈即可向融合方案演进

2. **延迟处理是当前最大空白**：
   - 多篇论文（TCST 2024）证明 80ms 延迟在高速下产生米级误差
   - 本项目文档反复提及延迟但未实测、未补偿
   - **建议**：优先实施延迟测量，考虑 DKF 类补偿

3. **目标丢失应对**：
   - 最新研究（TAES 2026）用 MCL 实现视场外方位估计
   - 本项目上视相机视场有限，此问题更突出
   - **建议**：至少实现有界的方位外推，理想情况引入 MCL

4. **FOV 保持策略**：
   - 最新研究表明不必强制目标居中，只需保证不出视场
   - **建议**：放宽本项目的 frame centering 约束，释放机动自由度

**❓ 本项目的独特挑战（学术论文较少覆盖）**：
- **Betaflight 平台**：上述论文多用 PX4，本项目的 Betaflight MSP 路径缺少学术参考，需自行摸索
- **上视相机**：多数论文用前视相机，上视布局的视场保持问题更特殊
- **TTC 增益调度**：本项目用 TTC 调度增益，而多数论文直接用 PN 常数 N，本项目方案需自行验证

**关键建议排序**（结合最新研究）：
1. **立即实测端到端延迟**（多篇论文证明这是米级误差来源）
2. **借鉴 K=3 作为 PN 常数起点**（IEEE TIE 2025 仿真实飞验证值）
3. **末端考虑 IBVS 融合**（精度提升一个数量级）
4. **实现目标丢失后的方位外推**（上视相机视场受限）
5. **放宽 FOV 居中约束**（释放机动自由度）

### A.1 比例导引实际实现参考

根据维基百科关于比例导引的资料，该方法广泛应用于空对空导弹制导：

**核心公式**：
```
a_n = N × λ̇ × V_c
```
- `a_n`: 侧向加速度
- `N`: 比例系数（典型值 3-5）
- `λ̇`: 视线角速率
- `V_c`: 闭合速度

**关键参数选择**：
- **N 值越大**：拦截速度越快，但需要更大的控制权限
- **N = 3-5**：是工程中最常用的范围
- **时间延迟**：响应延迟会显著影响性能（生物系统研究显示 18-28ms 的延迟影响）

**变体类型**：
- Pure PN：加速度垂直于视线
- Augmented PN：补偿目标加速度
- Generalized PN：加速度与视线成固定角度

**对你的项目的启示**：
1. 你的方案使用 `g_eval = K(TTC) × λ̇`，其中 K(TTC) 类似于增益调度的 N 值
2. 建议初期测试使用固定 N=3，验证基础性能后再引入增益调度
3. 端到端延迟控制在 100ms 以内非常关键
4. 如果能获取闭合速度估计（而非仅 TTC），控制性能会显著提升

### A.2 视觉跟踪器性能对比

#### OpenCV 内置跟踪器

根据 OpenCV 4.13.0 文档，提供两种主要跟踪算法：

1. **TrackerCSRT** (Discriminative Correlation Filter with Channel and Spatial Reliability)
   - 优势：准确性高，对遮挡有一定鲁棒性
   - 劣势：计算量较大

2. **TrackerKCF** (Kernelized Correlation Filter)
   - 优势：速度快，适合实时应用
   - 劣势：对快速运动和遮挡敏感

**你的项目使用 KCF 作为备选方案是合理的**，但主要依赖 ByteTrack。

#### ByteTrack 实际性能数据

根据 ByteTrack GitHub 仓库的实际数据：

**性能指标**（MOT17 测试集）：
- **MOTA**: 80.3（多目标跟踪准确度）
- **IDF1**: 77.3（ID 保持率）
- **速度**: 30 FPS（V100 GPU）

**模型变体**：
- **bytetrack_nano**: 0.90M 参数，适合边缘设备
- **bytetrack_x**: 90.0 MOTA（最高精度）

**核心创新**：
- 传统跟踪器丢弃低置信度检测
- ByteTrack 利用低置信度检测恢复被遮挡目标
- 通过与现有轨迹的相似度区分真实目标和背景噪声

**实际部署经验**（来自文档）：
1. **需要调优的参数**：
   - 测试图像尺寸
   - 高分检测阈值
   - 不同场景需要定制化输入尺寸

2. **实际限制**：
   - MOT20 数据集需要裁剪边界框到图像范围内
   - 达到论文性能需要针对序列调参
   - 不同场景最优参数不同（如 1600×896 vs 1920×736）

**对你的项目的建议**：
- ByteTrack 在拦截场景（单目标为主）中可能过度设计
- 考虑简化为"最高置信度检测 + 卡尔曼预测"
- 重点关注 bbox 裁切和低置信度检测的处理策略
- 在实际飞行中监控 track ID 切换频率

### A.3 YOLO 模型性能实测数据

根据 Ultralytics 仓库（YOLO26 最新版本）的性能数据：

#### 模型规格对比

| 模型 | 参数量 | mAP | CPU推理(ONNX) | GPU推理(T4 TensorRT) |
|------|--------|-----|---------------|---------------------|
| YOLO26n | 2.4M | 40.9% | ~39ms | ~1.7ms |

**注**：速度指标基于 COCO val 图像在 Amazon EC2 P4d 实例上测量。

#### 对你的项目的具体建议

**硬件平台推荐**：

1. **Jetson Nano 4GB**：
   - 推荐使用 **YOLO26n** 或 YOLOv8n
   - 使用 TensorRT INT8 量化可能达到 15-20 FPS
   - 输入分辨率建议 416×416 或 480×480
   - 预期端到端延迟：50-80ms

2. **Jetson Orin Nano 8GB**：
   - 可以使用 **YOLO26s** 或 YOLOv8s
   - TensorRT 优化后可达 30+ FPS
   - 输入分辨率可用 640×640
   - 预期端到端延迟：30-50ms

**优化策略**：
- **TensorRT 加速**：性能提升 2-5 倍
- **INT8 量化**：再提升 1.5-2 倍，精度损失 < 1% mAP
- **动态分辨率**：
  - 远距离（目标小）：使用 640×640 或 800×600
  - 近距离（目标大）：降至 416×416 或 320×320
  - 可根据 bbox 大小自适应切换

**实际帧率预测**：
```
完整pipeline = YOLO推理 + ByteTrack + LOS/TTC计算 + 控制计算
            = 50-80ms + 5-10ms + 5ms + 2ms
            = 62-97ms
            ≈ 10-16 FPS
```

这**低于理想的 20-30 FPS**，因此优化 YOLO 推理是高优先级任务。

### A.5 技术选型的实际对比

#### 跟踪器对比总结

| 方法 | 精度 | 速度 | 多目标 | 遮挡鲁棒性 | 实现复杂度 | 推荐场景 |
|------|------|------|--------|------------|------------|----------|
| KCF | 中 | 快 | 否 | 差 | 低 | 单目标、实时性要求高 |
| CSRT | 高 | 中 | 否 | 中 | 中 | 单目标、精度要求高 |
| ByteTrack | 高 | 快 | 是 | 强 | 中 | 多目标、遮挡场景 |
| 简单检测+卡尔曼 | 中 | 最快 | 否 | 差 | 最低 | 单目标、简单场景 |

**你的选择分析**：
- 主要：ByteTrack（多目标能力，但单目标拦截可能过度设计）
- 备选：KCF（合理的备选）
- 建议：考虑增加"简单模式"（纯检测+卡尔曼预测），用于低计算资源或末端阶段

#### YOLO 版本选择

对于嵌入式设备（Jetson）：

**YOLOv8n / YOLO26n（推荐）**：
- ✅ 参数量小（2.4M），推理快
- ✅ TensorRT 优化后可达实时
- ⚠️ mAP 40.9%，检测距离受限
- 适合：Jetson Nano 或 Orin Nano

**YOLOv8s / YOLO26s（次选）**：
- ✅ 更好的精度（48.6% mAP）
- ⚠️ 需要 Orin Nano 或更好的硬件
- 适合：检测距离要求较高的场景

**权衡建议**：
- 优先保证帧率 > 15 FPS
- 其次关注检测距离（实测必须覆盖拦截需求距离）
- 考虑目标大小：近距离拦截对检测器要求相对低
