# 工程缺口分级报告

**依据文档**：`doc/工程评估报告.md`

**分级原则**：以能落地、能工程化为第一前提，不把学术前沿方案作为当前硬门槛。

**适用阶段**：从当前 AirSim/PX4 仿真验证，迁移到 Betaflight 实机台架、系留和低速目标测试。

## 分级标准

- **P0：阻塞项**。不关闭就不应进入带桨自主 RC 输出、系留自主控制或移动目标测试。P0 的核心是安全、基础可观测性、控制方向和闭环时间一致性。
- **P1：高优先级工程项**。不一定阻塞 log-only 或无桨测试，但会显著影响系留/低速飞行的稳定性、可调试性和扩包线效率。
- **P2：优化项**。对性能、鲁棒性或长期演进有帮助，但不是当前 Betaflight 实机落地的首要条件。

## 当前已有基础

当前仓库已经具备以下工程基础，不应重复定义为缺口：

- 纯视觉链路：`FrameDetection -> R_BC/R_IB -> 6D LOS KF -> TTC -> GuidanceEval`。
- AirSim/PX4 验证链路：支持 YOLO/ByteTrack、固定上视相机、TTC/VM、body-rate/attitude 输出和日志。
- Betaflight 适配层：`MSP_STATUS/MSP_ATTITUDE/MSP_ANALOG/MSP_RC` 读取、`MSP_SET_RAW_RC` 输出。
- RC 安全映射：`rate_gain_matrix`、通道映射、RC 限幅、斜率限制、watchdog、AUX gate。
- 日志系统：CSV + meta JSON，记录 MSP、视觉、LOS/TTC、setpoint、RC raw/final/clip/slew 和 safety gate。

因此，主要缺口不是“代码完全没有”，而是**实机参数、时序、标定、安全验收和数据闭环尚未完成**。

## P0 缺口

### P0-1 Betaflight 硬件闭环尚未实证

**问题**：仓库已有 MSP/RC 代码，但工程评估报告仍处于“准备转向 Betaflight 实机部署”。飞控型号、UART、MSP baud、Receiver 协议、Modes、Failsafe、Blackbox 等需要在真实硬件上确认。

**为什么是 P0**：MSP 能否稳定读取和发送、AUX 是否真正 gate 住控制、Failsafe 是否按预期动作，决定是否允许任何带桨控制。

**最小关闭标准**：

- 无桨运行 `examples/run_betaflight_log_only.py`，`telemetry_error` 为空或偶发且可解释。
- `roll_deg/pitch_deg/yaw_deg` 跟随机体手动姿态变化。
- `rc_in_ch*` 与 Betaflight Receiver tab 一致。
- `safety_state` 能按 `LOG_ONLY -> READY -> ACTIVE/FAILSAFE` 预期变化。
- 运行结束或 gate 失效时，`rc_active=0`，最终 RC 回中或 throttle 到 `neutral_throttle_us`。

### P0-2 RC 通道方向、throttle 和 `rate_gain_matrix` 未标定

**问题**：Betaflight 路径使用 `rate_gain_matrix @ g_eval` 生成 roll/pitch/yaw rate 候选量，再映射为 RC。示例配置中矩阵默认为全零，说明当前没有可上机的控制增益。

**为什么是 P0**：任一轴方向反了、通道顺序错了、hover throttle 错了，都会造成发散或失控。PX4 的 body-rate/thrust 参数不能迁移到 Betaflight。

**最小关闭标准**：

- 无桨确认 `AETR1234` 或实际通道顺序与 Receiver tab 完全一致。
- 分别注入小幅正/负 roll、pitch、yaw，确认 Receiver tab 和 Blackbox 方向。
- 写入 `throttle_min_us/throttle_hover_us/throttle_max_us/neutral_throttle_us`，悬停油门经系留或低风险悬停验证。
- `rate_gain_matrix` 从极小值开始，完成单轴阶跃/正弦响应记录。
- `rc_clipped_ch*` 和 `rc_slew_limited_ch*` 不出现持续饱和。

### P0-3 图像时间戳、MSP 姿态和端到端延迟未实测

**问题**：报告多次指出延迟是最大空白。当前算法依赖曝光时刻姿态 `R_IB(t_exposure)`，但真实相机、YOLO、Python 调度、MSP 轮询和 RC 输出的延迟尚未量化。

**为什么是 P0**：如果姿态查表使用了错误时间，LOS 会带系统偏差；如果端到端延迟达到 80-150ms，末端会产生米级误差，继续调增益只会掩盖问题。

**最小关闭标准**：

- 记录并区分 `camera exposure -> detection -> guidance -> MSP_SET_RAW_RC -> Betaflight response` 的延迟。
- 日志中 `attitude_age_s`、`telemetry_age_s`、`watchdog_age_s` 在阈值内稳定。
- 若总延迟超过约 `100ms`，必须先降包线并加入简单 LOS 预测或更保守限幅。
- 明确 `AttitudeHistoryBuffer` 使用的时间基准和相机时间基准之间的偏差处理方式。

### P0-4 相机内参归档和曝光时刻未完成；固定上视外参已实机验证

**当前状态**：本机640x512内参和畸变候选已接入；固定安装外参已由2026-09-02固定目标动作验证为
`R_BC=[[0,1,0],[1,0,0],[0,0,-1]]`，各姿态惯性LOS残差小于5 deg。仍缺内参原始标定文件归档、
硬件曝光时间戳及飞行振动后的安装保持性证据。

**为什么是 P0**：内外参错误会直接把目标方向转错，后续 LOS KF、TTC、控制映射都会在错误输入上工作。

**最小关闭标准**：

- 写入实机相机 `width/height/fx/fy/cx/cy`，若是广角镜头需明确畸变处理策略。
- 保留2026-09-02静态目标验证和显式`R_BC`，相机拆装后重复同一动作检查。
- 归档棋盘格原图、标定脚本输出和重投影误差，消除`unarchived_candidate`状态。
- 获取或标定硬件曝光时刻，并在带桨振动日志中复核`lambda_I_*`稳定性。

### P0-5 实机 YOLO/ByteTrack 检测连续性未达最低门槛

**问题**：报告显示检测率对成败影响极大；S 机动中检测率低于约 40% 基本失败。实机环境的光照、运动模糊、目标姿态和背景与 AirSim 差距明显。

**为什么是 P0**：如果目标不能稳定检测，watchdog 会频繁退出 active；如果误检或 track id 频繁切换，LOS/TTC 会被污染。

**最小关闭标准**：

- 在目标距离、角度和光照覆盖测试包线内，记录检测率、连续漏检长度、track id 切换率。
- 初始测试包线内检测率建议达到 `>=80%`；低于该值不进入移动目标闭环。
- `detector_reject_reason`、`bbox_clipped`、`los_innovation_norm` 能解释每次失效。
- 明确 YOLO 模型、class id、conf/iou/imgsz、device 和 ByteTrack 参数。

### P0-6 人工接管、Failsafe 和测试边界未实证

**问题**：代码有 `--allow-control`、AUX gate、watchdog 和低电压 gate，但人工接管和 Betaflight Failsafe 必须在真实飞控配置中验证。

**为什么是 P0**：任何自主控制前，必须证明飞手可以立即接管，通信或视觉失效不会保持上一帧控制。

**最小关闭标准**：

- AUX 关闭立即让 `rc_active=0`，Receiver tab/Blackbox 可见。
- 遥测断开、目标丢失、低电压阈值触发、watchdog 超时均进入非 active。
- 明确 ARM/PREARM、MSP Override 或等效模式配置。
- 系留/围栏/软目标/急停流程写入测试卡，现场按卡执行。

## P1 缺口

### P1-1 缺少系统化的 Betaflight 标定工具

**问题**：报告提出需要开发台架标定脚本，但当前主要依赖运行脚本和 CSV 日志人工分析。

**影响**：不阻塞第一次无桨测试，但会显著拉长 `rate_gain_matrix`、RC 斜率和 hover throttle 的调参周期。

**建议关闭方式**：

- 增加离线/台架脚本：输入一组虚拟 `g_eval`，输出 `sp_*` 和 `rc_*` 曲线。
- 增加 Blackbox 与仓库 CSV 时间对齐脚本。
- 输出单轴阶跃响应摘要：延迟、超调、饱和率、slew 触发率。

### P1-2 TTC 质量门控仍偏基础

**问题**：已有面积过小、面积突变、裁切、TTC out-of-range 等门控，但报告指出 bbox 面积受姿态、曝光、模糊和检测框抖动影响很大。

**影响**：系统可以先用 LOS/VM 或 TTC soft guidance 跑低风险测试，但 TTC 不稳定会导致增益跳变和误导。

**建议关闭方式**：

- 增加 bbox 长宽比突变、中心跳变、亮度突变或面积方差指标。
- 对 `ttc_s` 增加连续性检查和置信度 hysteresis。
- 规定 TTC 失效时的降级：固定小增益 LOS/VM，而不是直接放大末端指令。

### P1-3 低帧率下的预测和丢检保持策略不足

**问题**：AirSim/PX4 runner 有 terminal image KF、frame guard、terminal accel hold；Betaflight runner 当前主要是通用 `PureVisionGuidancePipeline` + watchdog，未复用 PX4 末端状态机。

**影响**：低速低风险测试可以先跑，但移动目标和近距末端会频繁进入 `DEGRADED`，导致命令断续。

**建议关闭方式**：

- 在 Betaflight runner 中实现有界短时 coast：只允许 `0.2-0.5s`，且受 AUX、watchdog、RC 限幅约束。
- 丢检期间只保留低幅 yaw/roll/pitch 或中性策略，不盲目保持大命令。
- 日志增加 loss-hold 状态、hold age 和 hold source。

### P1-4 YOLO 推理优化尚未形成工程基线

**问题**：报告建议 TensorRT、INT8、模型大小对比，但当前缺少实机硬件上的 FPS、延迟和精度基线。

**影响**：如果当前硬件能达到目标 FPS，则不阻塞；如果实际只有 8-10 FPS，会严重限制末端控制。

**建议关闭方式**：

- 在目标硬件上跑 `YOLO + ByteTrack + pipeline` benchmark，记录平均/P95 延迟。
- 以 `>=15 FPS` 作为低速移动目标测试的最低线，`>=20 FPS` 作为扩包线目标。
- 先比较 YOLOv8n/s 和输入分辨率，不急于做复杂模型。

### P1-5 缺少清晰的工程指标与包线验收表

**问题**：报告给出了 CEP、最小脱靶、检测率、控制饱和等指标，但没有转化成每一阶段必须通过的验收表。

**影响**：容易跳阶段或靠主观判断继续测试。

**建议关闭方式**：

- 为无桨、系留、静止目标、慢速移动目标分别定义通过/停止条件。
- 每轮必须记录：检测率、最长连续漏检、LOS P95、RC 饱和率、slew 触发率、最小距离、人工接管次数。
- 任一 P0 gate 触发即停止扩大包线。

### P1-6 单目标跟踪策略需要简化和稳态化

**问题**：ByteTrack 适合多目标，但拦截多为单目标；track id 切换会重置 LOS/TTC，报告也指出这会引入瞬态。

**影响**：不阻塞基础验证，但会影响目标接近画面边缘、短时遮挡和末端裁切场景。

**建议关闭方式**：

- 增加单目标锁定策略：确认 M 帧后锁定目标，不因其他高分框立即切换。
- 对伪 track id 或短时 id 切换做 hold，而不是立即 reset。
- 记录 track switch count，作为是否进入移动目标测试的门槛。

### P1-7 Betaflight 状态解析和配置一致性仍偏弱

**问题**：当前 `mode_flags`、`sensor_flags` 以整数记录，文档也指出未解析成固件版本相关 mode 名称。

**影响**：不阻塞控制，但降低现场诊断效率；Betaflight 版本差异会让 Modes/Failsafe 排查变慢。

**建议关闭方式**：

- 在 meta 中记录 Betaflight variant/version/API 后，补充版本相关 mode flag 解释表。
- 将 Configurator 关键配置导出或截图归档到测试记录。
- 把 UART/MSP/Receiver/Modes/Failsafe/Blackbox 作为测试前 checklist。

## P2 缺口

### P2-1 多尺度 TTC 或光流 TTC

**说明**：报告建议用 bbox 宽度、高度、几何平均或光流增强 TTC。这能提升鲁棒性，但会增加计算和调参复杂度。

**当前建议**：先把现有面积 TTC 的质量门控和降级做好；只有在实测显示 TTC 是主要瓶颈时再做。

### P2-2 IBVS + PNG 融合

**说明**：报告引用最新研究认为 IBVS+PN 可提升末端精度。这个方向有价值，但不是第一阶段 Betaflight 落地的硬条件。

**当前建议**：先完成纯 PNG/LOS 的实机低速闭环；若目标常在视场边缘或末端误差大，再增加简单图像误差反馈，不直接上复杂 IBVS。

### P2-3 目标机动预测、IMM、MCL 方位估计

**说明**：这些方法能改善机动目标和视觉丢失后的再捕获，但实现复杂，计算量和调参成本较高。

**当前建议**：第一版只做有界短时外推和严格退出；等基础包线稳定后，再评估加速度模型或 IMM。

### P2-4 低成本测距传感器融合

**说明**：毫米波雷达、ToF 可改善距离和闭合速度估计，但增加硬件、重量、供电和融合复杂度。

**当前建议**：若单目 TTC 在真实数据中持续不可靠，再作为工程备选；不要在初期同时引入太多变量。

### P2-5 动态分辨率、自适应增益和在线学习

**说明**：这些能提高性能，但需要可靠的数据闭环和大量测试样本。

**当前建议**：先固定模型、固定分辨率、固定小增益建立基线；再做动态调度。

### P2-6 多机协同和端到端学习

**说明**：报告中列为长期方向。它们不是当前 Betaflight 单机实机部署的工程目标。

**当前建议**：暂缓，不进入近期路线图。

## 近期落地顺序

1. **关闭 P0-1/P0-6**：无桨 Betaflight MSP、AUX、Failsafe、回中策略验证。
2. **关闭 P0-2**：RC 通道、throttle、`rate_gain_matrix` 极小增益台架标定。
3. **关闭 P0-3/P0-4**：实测延迟，完成相机内外参和姿态时间对齐。
4. **关闭 P0-5**：在目标硬件上验证 YOLO/ByteTrack 检测率和连续性。
5. **推进 P1-1/P1-5**：做标定和验收脚本，把测试推进变成数据门槛。
6. **推进 P1-2/P1-3/P1-6**：增强 TTC、短时丢检保持和单目标锁定。
7. **P2 仅在实测瓶颈明确后进入**：不在第一轮上机中引入 IBVS/MCL/多传感器融合。

## 一句话结论

当前项目的 P0 不是“算法不够先进”，而是**实机闭环的硬件、时间、标定、安全和检测连续性还没有被数据证明**。先把这些基础工程门槛关闭，再谈 TTC 改进、IBVS 融合或机动预测，才符合可落地的推进顺序。
